# Historical bootstrap audit — 2026-09-08

The native module loader is **BLOCKED**. The Lua execution-recovery adapter is
implemented and host-tested, but has **no device result**. These are separate
gates. Evidence: `EVID-BOOTSTRAP-4139-002.json`.

The previous generated config exposed candidate absolute call addresses despite

macros for incomplete custom platforms, including Band 11 and Band 9 Pro.

## Why the Band 9 loader cannot simply be enabled

The portable ELF parser/relocator is reusable. The existing stage-0 memory,
stage-1/stage-2 firmware ABI, heap selection, memory publication, and Supervisor
platform adapter are not proven for this target.

There is also a concrete incompatible structure: Band 9's custom registration
in `canopus_supervisor_platform.c` writes inode type **7** and private data at
**+0x1C**. Band 11's stock routine writes type **1** and private data at
**+0x18** (fops remains +0x10). Copying the Band 9 code corrupts the Band 11 inode.
The Band 11 helper also returns reserve errors, whereas the Band 9 workaround
exists because that firmware's wrapper discards those errors.

The recovered malloc/free pair uses the user heap. It does not establish the
Kmem allocator required by the current Band 9 stages, executable memory,
cache coherency, MPU ownership, or a safe SRAM cave. NSH `mw/exec` command
presence is insufficient to establish any of those properties.

The initial report's successful Rust builds use `targets/static_candidate.rs`:
its identity guard and firmware operations return `ERR_UNSUPPORTED=-38`.
Those modules can pass ELF verification while intentionally doing no firmware
work. No Band 11 Supervisor was built by the original script's target case
statement, and no functioning Manager has been demonstrated.

Required before enabling native installation:

1. Device confirmation of command access and its actual execution context.
2. Exact allocator/free, executable mapping, MPU ownership and cache policy.
3. An owned stage-0 region, publication/restore protocol and failure reporting.
4. Stage-1/stage-2 entry and cleanup checks with an inert constructor.
5. Correct Band 11 inode/fops, Supervisor and LVGL v9 Manager ABIs.
6. On-device constructor, control-device and native-app registration gates.

No `bootstrap.toml` with invented MPU/cave addresses is created.

## Lua execution recovery

`lua-recovery.toml` binds the adapter to the exact version/build/hash and native
entry addresses. It is bootstrap metadata, not a general callable symbol pack.
The ROMFS `/etc/build.prop` is read before any recovery attempt; this avoids
requiring `getprop` through the still-missing `os.execute`. At runtime version
and build are compared; the firmware SHA-256 is a build/evidence binding, not a
claim that the Lua code hashes the running firmware.

During initial script loading, `debug.getinfo` exposes the active native pmain
and `debug.getlocal` exposes its path and loop lightuserdata. **September 10
correction:** the first-use loop getter pops the root lightuserdata; slot 3
then contains pmain's error handler. The updated adapter uses the cached
root context with temporary dataman isolation. See
[startup fix](pmain-startup-fix-2026-09-10.md) for firmware evidence and tests.
The adapter requires the exact pmain function address, temporarily removes
`_LOADED.os`, and uses `__newindex` to intercept the full OS table produced by
`luaopen_os`. It retains the exact native execute function, raises a private
sentinel into its own `pcall`, restores the registry and OS table, then restores
only `os.execute`. It never constructs a callable from an integer address.

**Known reentry cost:** pmain allocates a duplicate script path before opening
the libraries. The early sentinel skips that allocation's free. One attempt per
Lua state is enforced; reloading into another state can leak another path.
Native preamble operations are repeated with the checked root context. This
is a diagnostic recovery candidate, not a device-proven production mechanism.
The root lightuserdata points into a native stack frame, so deferring reentry
until a timer or click is invalid. Recovery runs while the entry script loads;
the recovered function itself can be used by subsequent clicks.

The Band 11 page only offers a one-shot `echo CANOPUS_EXEC_OK` test after recovery.
It does not offer Supervisor installation, destructive cleanup, or memory writes.
The log/return status is the next device evidence to collect. Recovery success
does not remove the native-loader blockers above.

## Host validation

The binary contains `Lua 5.4.0` at file offset `0xB1B9F7`. The C-frame fixture
and generated entry were tested with upstream Lua **5.4.0** and the installed
Lua **5.5**. The fixture uses real C activation records and `luaL_requiref`, but
substitutes a C command stub, so tests do not execute host shell commands. It
covers successful restoration, one-attempt behavior, identity/version mismatch,
unreadable identity, missing debug/frame, registry/metatable mismatch, unexpected
execute address, native-init error, registry restoration, and the one-shot UI.
It does not emulate the Band 11 native preamble, MPU, or hardware.

Lua 5.4.0 source was obtained from the [official archive](https://www.lua.org/ftp/)
and its SHA-256 matched
`eac0836eb7219e421a96b7ee3692b93f0629e4cdb0c788432e3d10ce9ed47e28`.
No downloaded interpreter or third-party source is part of the staged resource
ZIP. The standard host suite compiles the fixture against the locally installed
Lua headers when available:

```sh
python3 -B -m unittest discover -s scripts/tests -p 'test_band11_installer.py' -v
```
